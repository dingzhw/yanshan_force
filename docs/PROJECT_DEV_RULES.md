# 《烟山行动 · Yanshan Force》项目级开发与验收规则（v1.1）

> 适用于本项目开发、验收、打包与发布。具体工作范围和操作授权按用户指示执行。  
> 项目目标是让小学生愿意复玩，离开游戏后仍能独立认词与拼写。目标设备为 Windows 11、Ryzen 7 5700G / Radeon Vega 8、1280×720，普通行动的现实局长目标为 5–8 分钟。

## 规则一 · 小版本计划与试点

1. 每个小版本从可追溯基线出发。开工前简要说明本版要解决的问题、范围、阶段结果和验收依据。计划通常一页内够用，阶段数随工作量调整。单点修复可在任务记录中说明范围和检查。
2. 存档丢失、学习统计失真、严重启动卡顿或发布入口错版，优先处理受影响的推进环节。能独立完成的工作可继续，交付记录写明未解决项及其影响。
3. 试点注明场景、目的、配置和复审条件。在扩展到其他场景或下一次相关改动前，按试玩及回归结果决定保留、推广或回退。确有场景差异时可保留专用配置，并说明依据。

## 规则二 · 性能基线与行为校验

1. 性能优化先测可比基线。启动优化按阶段计时，帧时和内存优化从有代表性的场景取样。复用能定位瓶颈的日志或分析器数据，记录影响比较的硬件、构建和运行条件。
2. 改动地形、碰撞、计分等核心路径时，先明确应保持的量与本版预期变化。对保持项用有代表性的点位、边界或存档做新旧对照。数值量按单位和实际影响设容差，需精确一致的离散结果做精确比较。有意调整的规则按新预期验收，同时检查相邻行为是否回归。
3. 帧间隔用单调时钟测量，例如 `Time.get_ticks_usec()`。记录版本、CPU/GPU、后端、驱动、分辨率、3D 倍率及垂直同步或限帧状态。测吞吐上限可关闭垂直同步，判断默认体验要使用玩家实际档位和设置。报告同时列平均 FPS、P95 和最长帧。低档以约 33.3 ms 的 P95 作为 30 FPS 参照，首入尖峰单独记录。
4. 图形启动注明计时起止，例如从进程启动到首个可操作的菜单帧。首次采样与复开分别记录，并交代应用及驱动缓存状态。冷热比较使用同一成品和设定，缓存状态不明时按实际运行条件命名。无窗口构建耗时单列。5 秒等限值按该版本计划判定。
5. 涉及整体性能验收时，覆盖正常启动、自由靶场路线及有代表性的交战段，现有巡检可选普通首营与 B 区。局部性能修复可围绕受影响场景复测。注明用脚本采样还是人工走完整局。

## 规则三 · 可读性与证据

1. 涉及词盾、遮挡、相关 UI 或渲染改动时，从正常接近路线选点，用较长词组和不利的侧向角度找遮挡。逐档对拍时固定机位、朝向和影响结论的场景状态，记下实际后端及 3D 倍率。影响通用画质或词盾时覆盖标准、F6 低档和 GL 低档。脚本摆位、脚本行进和人工试玩分别注明。
2. 目标机性能、学生首局时长和次日脱机回忆各自验收。对应项目须有符合本版要求的原始记录才标为通过。布尔字段在未测或未通过时均为 `false`，验收记录区分两种情况，并在开头写明影响交付的限制。以学生实际从开局到结算的用时核对 5–8 分钟。
3. 版本验收留存简明记录。可复算的数据写入 `复核数据.json` 或等效结构化报告，包括版本或构建标识、环境、测试方法和结果。按本版改动附上基线对照、帧时、截图及其哈希、回归计数和包哈希等适用证据。

## 规则四 · 存档与学习数据

1. 有活动对局时，成功、阵亡、超时、主动放弃、切换行动及正常关窗均应结算学习记录、待复测队列和实际用时 `wall_clock_seconds`。未撤离的背包物品按游戏规则清空，学习记录独立保存。异常中断的恢复能力单独说明。
2. 涉及存档结构或学习统计口径变化时，明确旧字段如何迁移。用隔离样档验证旧数据可读、新数据可保存、原档受保护。可采用写入新文件或保留可恢复备份。解析失败要保护原档并提示，写盘要检查临时文件写入和目标替换的结果，失败时保留上一份可用记录并提示。
3. 主词包与句库按稳定 ID 各算分子分母。独立识词按每题首次有效选择计入，保留候选数和提示状态。只剩一个候选时，游戏分和动作反馈照常，独立掌握度不因这次选择增加。
4. 拼写保留提示和照录后继续开箱的路径。独立答对 `independent`、借助提示或纠正后答对 `hinted`、照录 `copied_scaffold` 分开记录。按当前规则，只有独立拼写计入掌握和完美破译，错答和受助作答进入待复测队列。玩家可从营地选择何时复测。
5. 明确每项统计的记录单位、分母和跨局口径。v0.6.7 的 `seen` 记录学习事件，同一道拼写题可分别记录首次错误和最终完成。需要见题数时按题另统计，重试和重复事件按已声明的口径处理。掌握数说明其判定依据，隔日保持以脱机复测为准。调整计数时验证旧档与新口径的衔接。
6. 词句、题库放入 `game/data/`。标为教材原句或词组拓展的条目可追溯到教材版本、印刷页和原件指纹，并用 `source_kind` 等字段标类型。其他来源按实际标注。新增需导出的数据时检查 `game/export_presets.cfg` 和 `tools/verify_packaged.gd`，现有规则覆盖时可复用。

## 规则五 · 模块与画质

1. 优先改动业务所需的边界。可独立验证的学习、存档或场景逻辑按需抽出，模块大小由职责和可读性决定。
2. 改动深度重建、色调、抗锯齿或后端专属特性时，按实际后端能力设置条件或采用兼容实现。可复用 `CURRENT_RENDERER` 或 `RenderingServer.get_current_rendering_method()`。检查受影响后端的运行日志和画面，调整现有抗锯齿等默认值时做同场对照。
3. 命令行画质参数与 F6 共用设置入口，核对实际后端和生效的 3D 倍率。F6 切换当前后端的画质，后端由启动入口或运行环境决定。

## 规则六 · 打包与发布验收

1. Windows 包内与根目录的启动、巡检脚本由 `tools/release_playtest.py` 的同一逻辑生成。核对普通入口、低负载入口、巡检入口的版本指向与同档参数。
2. 交付新的 Windows 验收包或正式包时，从实际导出的同一套 EXE/PCK 做启动和资源核验。使用独立 PCK 执行适用于成品的既有回归和 `tools/verify_packaged.gd`。编辑器或导入流程专用检查按其运行环境记录。回归与巡检使用隔离的测试存档和输出位置。
3. 在 `docs/release-<ver>.json` 记录 EXE/PCK/ZIP 的字节数、SHA-256 和来源检查点，并核验 ZIP CRC。保护已交付的历史包。涉及替换或归档时，先按上级工作约定备份并校验受影响的产物。
4. 本地验收包用于补齐目标机或家庭数据，按实测标明已完成和待验项。正式发布前按当版计划核对放行条件及授权。需提前共享预览包时，注明用途和限制，并遵循对外分发授权。

## 规则七 · 儿童体验与文档

1. 首屏优先显示选单元、普通行动、模式选择、复测和简明进度。改装、图鉴与详细日志可收进二级界面，入口清楚可找。
2. 交战时让中文题干、英文词盾和必要的危险提示易于辨认。与作答争夺视线的地名大标牌等可淡出或收起，保留辨路所需提示。
3. README、更新日志、试玩说明与验收记录用平实语言说明改动、实测条件与限制。打包时同步核对 `VERSION`、`docs/project-scope.json`、`CHANGELOG.md`、`README.md`、`README.txt` 和对应版本的试玩说明。

## 规则八 · 授权、隐私与 Git

1. 核对本次拟提交、共享或随包分发的内容，包括截图及其元数据、日志、JSON 和配置。移除未经授权的个人信息、账号数据及本机绝对路径。按许可保留素材归属和获准公开的署名。本地机器配置和未经处理的原始材料按用途留在本地。
2. 新增第三方素材时核对使用与分发许可，更新 `game/THIRD_PARTY.txt` 及 `game/licenses/` 中受影响的内容。
3. Git 暂存、提交、打标签、推送和对外发布按各自动作的授权办理。本地验收成果可留在工作区。获准提交或打标签时，核对仓库、分支、拟纳入的路径和验证结果，标签指向已核验的提交。已有改动与本地归档按上级工作约定保留。

- [ ] 受影响的算法、玩法、存档迁移和学习口径完成对照与回归。
- [ ] 受影响的档位、首屏、场景帧时或读词画面有证据，目标机与学生数据按实填写。
- [ ] 若交付 Windows 包，已核对成品启动、PCK 资源与适用回归、入口参数、发布清单、ZIP 与历史保护。
- [ ] 若办理 Git 交付或对外分发，已核对相应授权、拟交付范围、隐私与素材许可。正式发布已符合当版放行条件。
